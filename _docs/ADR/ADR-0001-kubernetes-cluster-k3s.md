# ADR-0001: Вибір k3s як дистрибутива Kubernetes для лабораторного кластера

* **Status:** Accepted
* **Date:** 2026-10-19
* **Authors:** Alex.Viki

## Context
Для виконання практичних завдань курсу **Kubernetes in Production (Module 02 – Security & Policy as Code)** необхідно розгорнути повноцінний Kubernetes кластер на віртуальній машині під керуванням Ubuntu 24.04 LTS. На початковому етапі на сервері не було встановлено жодного контейнерного рантайму (Docker/containerd) або інструментів оркестрації (`kubectl`, `kubeadm`, `kind`, `minikube`).

Вимоги до кластера:
- Мінімальне споживання ресурсів (CPU/RAM), щоб залишити достатньо потужності для роботи контролерів безпеки (Kyverno) та робочих навантажень студентів і ментора.
- Повна сумісність зі стандартним Kubernetes API (RBAC, Admission Webhooks, Namespaces, ServiceAccounts).
- Швидке розгортання та збереження стану після перезавантаження VM без додаткових прошарків віртуалізації.

## Options Considered
1. **Option A: k3s (Lightweight Kubernetes від Rancher/SUSE)**
   * *Pros:* Єдиний бінарний файл, який включає `containerd`, `kubectl`, CNI (Flannel), CoreDNS; запускається як системний сервіс `systemd`; споживає мінімум оперативної пам'яті (~512MB); не потребує попереднього встановлення Docker.
   * *Cons:* Використовує SQLite за замовчуванням замість etcd (для single-node), має деякі вбудовані компоненти (Traefik, ServiceLB), які можуть бути зайвими у специфічних сценаріях.
2. **Option B: kind (Kubernetes in Docker)**
   * *Pros:* Швидке створення та видалення тестових кластерів, зручно для локальної розробки та CI/CD.
   * *Cons:* Потребує попереднього встановлення Docker; працює поверх контейнерів (Docker-in-Docker), що додає накладні витрати та ускладнює мережеву взаємодію і персистентність після перезапуску хоста.
3. **Option C: Minikube**
   * *Pros:* Широко відомий інструмент для навчання, має багато аддонів.
   * *Cons:* Вимагає драйвер віртуалізації або Docker; споживає більше ресурсів і повільніше стартує порівняно з k3s.
4. **Option D: kubeadm**
   * *Pros:* Максимально наближений до «ванільного» Kubernetes.
   * *Cons:* Висока складність ручного налаштування (окреме встановлення containerd, kubelet, kubeadm, CNI-плагіна), що не є ціллю модуля з Policy as Code.

## Decision
Ми вирішили використати **Option A: k3s** для розгортання базового кластера Kubernetes (скрипт `module-02/setup-cluster.sh`).

## Rationale
`k3s` забезпечує найкращий баланс між швидкістю інсталяції (одна команда без залежності від Docker), низьким споживанням ресурсів на Linux VM та 100% сумісністю з механізмами RBAC і Dynamic Admission Control (Mutating/Validating Webhooks), які необхідні для роботи Kyverno.

## Consequences
* **Positive:**
  - Кластер розгортається менш ніж за хвилину і автоматично піднімається через `systemd`.
  - Вбудований `kubectl` та `containerd` працюють одразу з коробки.
  - Конфігурація `/etc/rancher/k3s/k3s.yaml` легко експортується у `~/.kube/config` для адміністратора кластера.
* **Negative / Risks:**
  - Інсталяція `k3s` на хост вимагає привілеїв `sudo`.
  - Для очищення всього кластера потрібно запускати `/usr/local/bin/k3s-uninstall.sh`.
